A document system for your Laravel application.

## Installation

```bash
composer require skyraptor/laravel-documents
```

The package requires `spatie/laravel-pdf` 2.10 or later in the 2.x series for
builder-level caching controls and PDF post-processing. Each PDF backend has its own
requirements. For Spatie's default Browsershot driver, also install
`spatie/browsershot` and its Node.js, Puppeteer, and Chrome prerequisites. See
the [Spatie Laravel PDF documentation](https://spatie.be/docs/laravel-pdf/v2/introduction)
for the available drivers and their requirements. Other PDF backends, versioned
storage, and progress tracking remain optional.

Publish the configuration to customize the snapshot cache:

```bash
php artisan vendor:publish --tag="laravel-documents-config"
```

The base package does not require database migrations. Optional versioned
storage and coalesced generation have their own migration setup described below.

## Usage

Define a document around the subject being rendered:

```php
use App\Models\Invoice;
use SkyRaptor\LaravelDocuments\Documents\Document;

class InvoiceDocument extends Document
{
    public static ?string $view = 'pdf.invoice';
    public static ?string $disk = 'documents';

    public function __construct(public Invoice $invoice) {}

    public function path(): string
    {
        return "invoices/{$this->invoice->getKey()}.pdf";
    }

    public function data(): array
    {
        return ['invoice' => $this->invoice];
    }
}
```

Rendering resolves the data and Blade view immediately. It produces a readonly,
serializable `RenderedDocument` containing the HTML, target context, and
configuration identifiers. The PDF job receives that result, not the document
or its model:

```php
use SkyRaptor\LaravelDocuments\Facades\Documents;

$document = new InvoiceDocument($invoice);
$job = Documents::makeJob($document); // Resolve data and freeze HTML now.
$generationId = $job->generationId();

dispatch($job);                      // Generate and publish on the worker.

$document->exists();
$document->get();                    // Current PDF contents.
```

For synchronous use, generate once and publish those exact contents:

```php
// Render once and generate final PDF bytes without storing anything:
$generated = Documents::generate($document);
$pdf = $generated->contents;

// Publish the result without rendering or generating again:
$version = Documents::publish($generated);
```

Alternatively, `Documents::publish($document)` performs all three stages in
one call.

The `Documents` facade resolves `DocumentWorkflow`, which coordinates these
document-level operations. Passing a `Document` renders it once; passing a
`RenderedDocument` skips rendering, and publishing a `GeneratedDocument` skips
both rendering and generation. The workflow retains no state between calls:
pass the generated result, not the original document, to reuse generated bytes.
`makeJob()` and `makeJobIfChanged()` only create jobs and never dispatch them. Pass `connection:`,
`queue:`, or `job:` to configure a job. By default, the document's configured job
is used, falling back to its storage configuration's default.

Prefer constructor-injecting `DocumentWorkflow` when desired; it exposes the
same methods as the facade. In application tests, use Laravel's facade mocking,
for example `Documents::shouldReceive('generate')->once()->with($document)->andReturn($generated)`.

Rendered results contain HTML and generated results contain PDF bytes, which
can include sensitive data; protect serialized payloads accordingly. Jobs do
not use Laravel's `SerializesModels` trait.

### Explicit lifecycle stages

The stage outputs are immutable and serializable:

```text
Document -> render() -> RenderedDocument
         -> generate() -> GeneratedDocument
         -> publish() -> stored version (or null)
```

Use the focused services when coordinating stages explicitly:

```php
use SkyRaptor\LaravelDocuments\DocumentPublisher;
use SkyRaptor\LaravelDocuments\DocumentGenerator;
use SkyRaptor\LaravelDocuments\Jobs\DocumentJobFactory;

$rendered = $document->render();
$generated = app(DocumentGenerator::class)->generate($rendered);
$version = app(DocumentPublisher::class)->publish($generated);
```

Alternatively, queue the rendered revision **instead of** generating it now:

```php
dispatch(app(DocumentJobFactory::class)->make($rendered, job: $document->job()));
```

`DocumentGenerator` accepts only rendered input and returns a `GeneratedDocument`
with final, post-processed `contents`, `target`, `fingerprint`, and `generationId`.
Opted-in results also carry the rendered request's `snapshotId`.
It does not retain the rendered HTML. `DocumentPublisher` accepts only that
generated result and coordinates storage, snapshot-cache updates, and publication
events; it has no generator dependency. `DocumentJobFactory` creates jobs from
rendered input. No service is serialized into either result or a job.

Use `publishWithResult()` when the caller must distinguish a completed write
from a superseded attempt:

```php
use SkyRaptor\LaravelDocuments\DocumentPublicationStatus;

$result = Documents::publishWithResult($rendered);

if ($result->status === DocumentPublicationStatus::Superseded) {
    abort(409, 'The requested PDF was superseded. Please try again.');
}

$version = $result->version; // null for unversioned storage
```

`Documents::publishWithResult()` accepts the same inputs and `generationId` as
`publish()`. `DocumentPublisher::publishWithResult()` accepts a generated result.
The result reports `Published` with the storage version (which may be null), or
`Superseded` with a null version. Generation, storage, and cache failures still
throw. The existing `publish()` return value is unchanged: null can mean either
an unversioned write or a superseded attempt.

An outcome describes that publication attempt, not a guarantee that its target
remains unchanged afterward. Applications are responsible for deciding how to
respond and for any availability or freshness checks needed before serving it.

Each workflow invocation renders, generates, and writes at most once. Explicitly
publishing the same result again can write again, and queue retries can repeat
generation and publication; this is not an exactly-once queue guarantee.

### PDF driver configurations

The `default` PDF configuration resolves Spatie's `PdfDriver` from the Laravel
container when generation runs. Configure Spatie's default driver or register
additional named configurations in a service provider that runs in every
application and worker:

```php
use SkyRaptor\LaravelDocuments\Pdf\DocumentPdfDriverManager;
use Spatie\Browsershot\Browsershot;
use Spatie\LaravelPdf\Drivers\BrowsershotDriver;
use Spatie\LaravelPdf\PdfBuilder;

app(DocumentPdfDriverManager::class)->register(
    'invoice-v1',
    fn () => (new BrowsershotDriver(config('laravel-pdf.browsershot', [])))
        ->customizeBrowsershot(
            fn (Browsershot $browser) => $browser
                ->waitUntilNetworkIdle()
                ->setOption('preferCSSPageSize', true),
        ),
    function (PdfBuilder $builder): void {
        $builder
            ->format('A4')
            ->meta(title: 'Invoice', author: 'Accounts');
    },
);
```

Select it with `public static string $pdfDriver = 'invoice-v1';` on the
document. A factory can instead return any Spatie `PdfDriver`, including a
custom implementation; the optional third argument configures a fresh Spatie
`PdfBuilder`. Use its methods for page settings, metadata, encryption, or
Browsershot customization. Margins default to zero and can also be changed there.
Browsershot drivers are cloned for generation so builder settings do not leak
into shared driver instances; factory-configured defaults are preserved.
Generation calls `generatePdfContent()`, so metadata and encryption are applied
before the final bytes are returned or passed to document storage. Encryption
requires Spatie's optional encryption dependencies. Post-processing failures
propagate and prevent storage of an unprocessed PDF.

The snapshot supplies the body HTML. Builder callbacks must not load the
document's data or render views; `view()`, `headerView()`, and `footerView()`
are rejected. Use previously rendered HTML for any headers or footers.
Spatie's PDF cache is disabled by default; a callback can explicitly enable it
with `cache()`. Automatic cache fingerprints include the registered configuration
identifier as well as Spatie's HTML and builder settings. Explicit cache keys
are used unchanged; make them unique across configurations unless sharing
cached output is intentional.

Only the identifier is serialized. The worker resolves its own factory and
builder configuration, so all processes must register the identifiers they use. Different
deployments may produce different results for the same snapshot if their
configuration changes. Use a new identifier when a configuration change should
also count as a snapshot change.

### Storage

The built-in `disk` configuration uses `DiskDocumentStorage`: it writes to the
document's resolved disk and path, replaces the existing file, and selects a
unique job per target. The built-in `versioned` configuration selects
`VersionedDocumentStorage` and a non-unique job. Install its optional dependency
and migrations before using it:

```bash
composer require skyraptor/laravel-versioned-storage:0.2.0-beta.1
php artisan vendor:publish --tag="laravel-versioned-storage-migrations"
php artisan migrate
```

Version `0.2.0-beta.1` is a pre-release tested with this package. It requires a
Unix-like runtime with PCNTL, POSIX, and sockets; native Windows PHP is not
supported. See its [installation guide](https://github.com/bumbummen99/laravel-versioned-storage#installation).
Set `public static string $storage = 'versioned';` on the document, then use
`$document->versions()` and `$document->get($version)` to read published
versions. The current version is the last successfully **published** version,
not necessarily the last dispatched or the last completed job.

Storage configurations are registered in the container, not on individual
documents. For example, register a second disk configuration:

```php
use SkyRaptor\LaravelDocuments\Storage\DiskDocumentStorage;
use SkyRaptor\LaravelDocuments\Storage\DocumentStorageManager;

app(DocumentStorageManager::class)->register(
    'long-write-disk',
    fn () => new DiskDocumentStorage(lockTimeout: 45),
);
```

Select it with `public static string $storage = 'long-write-disk';`. The
optional third registration argument is the default job class. Use a job whose
uniqueness and batch behavior match the storage's write guarantees.

For a database or other backend, implement the `DocumentStorage` contract and
register its factory in the same manager. Provide its serializable target
parameters with a readonly `DocumentStorageContext` subclass, and override the
document's `storageContext()`:

```php
use SkyRaptor\LaravelDocuments\Documents\Document;
use SkyRaptor\LaravelDocuments\Storage\Contexts\DocumentStorageContext;

final readonly class InvoiceRecordContext extends DocumentStorageContext
{
    public function __construct(public int|string $invoiceId) {}

    public function identity(): string
    {
        return 'invoice-record:'.$this->invoiceId;
    }
}

class StoredInvoiceDocument extends Document
{
    public static ?string $view = 'pdf.invoice';
    public static string $storage = 'invoice-records';

    public function __construct(public int|string $invoiceId) {}

    public function data(): array
    {
        return ['invoiceId' => $this->invoiceId];
    }

    public function storageContext(): DocumentStorageContext
    {
        return new InvoiceRecordContext($this->invoiceId);
    }
}
```

The context identity must be stable and unambiguous across all storage
configurations that may address the same target: it is used for unique jobs and
snapshot-cache locks. Contexts must contain immutable, serializable values, not
models, closures, connections, or storage instances. The built-in
`FilesystemDocumentStorageContext` contains the resolved disk name and a
Flysystem-normalized path. Different disk names pointing to the same physical
location are still distinct identities; use one disk name consistently.
Storage and driver factories are resolved separately in the worker.

### Skipping unchanged snapshots

```php
use SkyRaptor\LaravelDocuments\Facades\Documents;

if ($job = Documents::makeJobIfChanged($document)) {
    dispatch($job);
}
```

`Documents::makeJobIfChanged()` renders the document (or accepts an existing
`RenderedDocument`) and compares it with the last
successfully cached snapshot for the target. The comparison uses rendered HTML, target
context, and configuration identifiers, **not PDF bytes**. They do not detect a
deleted or externally modified PDF, changed external assets, or different
driver/storage settings under the same identifier. Use versioned asset URLs or
embed assets, change the relevant identifier when configuration changes, and use
`Documents::makeJob()` for a forced regeneration. Cache eviction also causes
regeneration. For an existing snapshot, use
`DocumentSnapshotCache::changed($rendered)` or
`DocumentJobFactory::makeIfChanged($rendered)`.

The snapshot cache defaults to Laravel's default cache store. Configure
`snapshot_cache.store` in the published `laravel-documents.php` config to select
another store. All publishers must use the same persistent, shared cache and
prefix, with atomic lock support; `array` is suitable only for a single process
and the `null` store is rejected. Set `snapshot_cache.lock_seconds` longer than
the worst-case storage write and `snapshot_cache.lock_wait_seconds` to an
appropriate contention timeout. Defaults are 300 and 30 seconds, respectively.
Partial configuration overrides retain defaults for omitted nested settings.
Unique-job locks and disk-storage write locks use Laravel's default cache store;
it must also support atomic locks and be shared across processes.
Unique-lock operations follow the active default store after cache switches or
driver purges in long-lived processes. Configure the same store and prefix for
dispatch and worker execution, before job deserialization, and keep that context
through cleanup. Switching stores does not migrate locks already held.

The lock serializes each target's storage publication and snapshot-cache update;
PDF generation itself can run concurrently. A failed storage write invalidates
the previous cached snapshot so a later comparison will regenerate. If caching
or releasing the lock fails after a successful storage write, the error is
reported rather than retrying the published job. Lock-release failures include
both exceptions and `false` results; they do not replace an original storage
exception, and locks are never force-released. The comparison and subsequent
dispatch are not atomic: simultaneous callers or already-running jobs can still
produce additional versions. External storage writes do not participate in this
coordination. A worker crash after storage can also cause a retry.

### Latest rendered snapshot wins (opt-in)

This section describes the default cache-backed policy. For database-backed
ordering with coalesced queued work, see **Coalesced generation** below.

Prevent an older queued snapshot from overwriting a newer synchronous HTTP
publication by enabling this policy on the document:

```php
public static ?bool $latestSnapshotWins = true;
```

Alternatively, set `'latest_snapshot_wins' => true` in the published
`config/laravel-documents.php` to enable it package-wide. The document property
defaults to `null` (inherit); `false` explicitly opts out. Override
`latestSnapshotWins(): ?bool` for instance-specific selection. Explicitly
constructed snapshots accept `new RenderedDocument($html, $target,
latestSnapshotWins: true)` and otherwise inherit the package default.

After HTML rendering succeeds, snapshot construction registers a new opaque
`snapshotId` in the shared snapshot cache under the target's publication lock.
This registration defines rendering completion and ordering; it does not use
worker timestamps or PDF generation completion. Snapshots with the same current
fingerprint share an ID and remain eligible to publish. A different fingerprint
supersedes earlier opted-in snapshots for that storage-context identity. If the
content changes from A to B and back to A, the new A gets a new ID and the
original A remains superseded. Snapshot IDs do not affect content fingerprints.

The immutable ID survives serialization and is copied into `GeneratedDocument`.
Generation, job creation from existing snapshots, publication, and retries do
not register the snapshot again. Under the same target lock, publication checks
the ID before writing or changing the stored fingerprint. Superseded results
write nothing, emit `DocumentSuperseded` instead of `DocumentStored`, and return
`null` from `publish()` or a `Superseded` result from `publishWithResult()`;
generation may still have run. The event includes `target`,
`generationId`, `snapshotId`, and `latestSnapshotId`. Its listeners run after
the lock is released. A built-in job's `generated()` is true after the completed
attempt, including a superseded one; it is not proof of storage.

The newest distinct rendered fingerprint wins even if its job is never dispatched,
is cancelled, or fails generation. Superseded results do not become eligible again.
Repeated publication of the latest result is still allowed. The policy applies
to disk, versioned, and custom storage through the common publication service;
superseded results do not create historical versions.

**Queue uniqueness is unchanged:** `GenerateUniqueDocument` still discards
duplicate dispatches. Rendering a different snapshot can supersede an older job
even if Laravel subsequently discards the newer job; an equivalent snapshot
does not. If every newer request
must be queued, select `GenerateVersionedDocument` (also usable with disk
storage), a non-unique custom job, or its progress-enabled equivalent.
This policy prevents stale writes; it does not schedule replacement jobs.
Equivalent snapshots may publish in either order. The fingerprint covers rendered
HTML, target, and driver identifier, not mutable external assets or changes to a
driver's implementation.

Rendering now needs the shared persistent cache when opted in, even for
generation without publication. All participating HTTP processes and workers
must use the same cache store and prefix, and opt in consistently. Untracked
snapshots, including explicitly opted-out and legacy payloads, retain the old
publication-order behavior. Registration failures propagate. Missing or evicted
latest-request markers fail publication explicitly rather than allowing stale
contents through; render a fresh snapshot to recover. Do not flush or change
the coordinating cache while workloads are outstanding. Atomic-lock lease
duration must exceed storage writes; external writes and expired lock leases
are outside the guarantee.

During a rolling upgrade, older processes still register a new ID for every
render, including equivalent renders. Existing UUID-only markers cannot be
matched to a fingerprint, so the first new registration supersedes them. Restart
all rendering processes to obtain the equivalent-snapshot behavior consistently.

### Coalesced generation (opt-in)

Coalescing keeps the newest pending rendered snapshot per target. One queue
wakeup normally processes it; a request arriving during generation replaces the
pending snapshot and the worker continues with the newest one. Intermediate
snapshots may be skipped. This mode currently requires the built-in `versioned`
storage and `skyraptor/laravel-versioned-storage` 0.2.0-beta.1 or a compatible
version. Install and migrate that package first, then publish and run the
Documents migration:

```bash
php artisan vendor:publish --tag=laravel-documents-migrations
php artisan migrate
```

Set `latest_snapshot_wins` and `coalescing.enabled` to `true` in
`config/laravel-documents.php`. Set `coalescing.connection` and
`laravel-versioned-storage.connection` to the same Laravel database connection
(both default to the default connection), and run both packages' migrations on
that connection. Every document rendered while coalescing is enabled must use
versioned storage and latest-snapshot ordering. Calls starting inside a database
transaction are rejected: enqueue after the caller's transaction commits.

```php
use SkyRaptor\LaravelDocuments\Facades\Documents;
use Illuminate\Support\Facades\Schedule;

// InvoiceDocument has public static string $storage = 'versioned'.
Documents::dispatchCoalesced($document, connection: 'redis', queue: 'pdf');

// Schedule the recovery command in the application's console routes:
Schedule::command('documents:recover')->everyMinute();
```

`dispatchCoalesced()` returns `false` if that rendered snapshot was already
superseded before it could be recorded, or `true` when it was accepted.
Dispatch errors throw even though the recorded request remains recoverable.

Pass a `Document` directly when queued work must survive a crash after it
supersedes earlier work. Its HTML is rendered first; the new ordering marker
and pending snapshot are then committed in the same database transaction. A
crash before that commit leaves the earlier marker and pending work unchanged.
This path calls `html()`, `target()`, and `pdfDriver()` directly; it does not
call an overridden `render()` method. Normal `render()` and synchronous
publication retain their existing behavior. Passing an already
`RenderedDocument` is also supported, but rendering it registered its marker
before dispatch, so a crash between those calls cannot recover that request.

Run Laravel's scheduler and queue workers continuously. The durable target row
is written before dispatch. If dispatch fails, the exception is raised and
recovery retries after `coalescing.lease_seconds`. Terminal worker failures,
crashes, and lost wakeups are also recovered; monitor failed jobs and command
errors. Choose a lease longer than normal queue delay and processing time to
avoid unnecessary duplicate attempts, and set the queue worker timeout below
its queue's retry/visibility timeout. Recovery can dispatch another worker after
a lease expires, so generation and wakeups are **at least once**, not exactly
once. Recovery keeps existing wakeups valid even when queue delay exceeds the
lease; overlapping workers can consequently process the same snapshot.
Queue connection and name for recovery follow the latest pending request.
Coalesced jobs do not implement the optional progress integration or batches.

Synchronous `publishWithResult()` uses the same database ordering and staged
publication, and HTML preview remains separate. A newer synchronous publication
supersedes older pending work; if the same snapshot is already current and the
PDF exists, the worker skips generation. Conversely, a newer queued snapshot
supersedes an older synchronous attempt. Registration order is defined after
rendering, not by source-record revision or the time a request started.

For synchronous generation that may reuse an unchanged PDF, call
`Documents::publishIfChanged($document)` (or pass an ordered
`RenderedDocument`). It returns a `DocumentPublicationResult`: an existing
version is reused only when its fingerprint matches and its file exists;
otherwise it generates and publishes normally. If a newer snapshot is
registered during the check, it returns `Superseded`. Reuse requires
coalescing and versioned storage, and must run outside a database transaction.
Unlike `publishWithResult()`, reusing a version does not emit a new
`DocumentStored` event. Versions published before the reuse migration are
regenerated once because their version identifier was not recorded.

`Documents::targetStatus($document->target())` exposes shared target state:
`NotScheduled`, `Pending`, `Published`, or `Tombstoned` from
`DocumentTargetStatus`. `Pending` includes queued, running, failed-attempt,
and recovery-waiting work; it is not a percentage or a terminal failure.
`Published` means the latest fingerprint was published, not that the physical
file has been checked at query time. A newer rendered snapshot that has not
been queued is `NotScheduled`. This state is shared by all requests for that
target, not attached to any individual job or requester.

Versioned writes are staged outside a transaction. The target's latest snapshot
check, current-version switch, and fingerprint update commit together on the
same database connection. An ID is journaled before a stage can become ready;
recovery discards abandoned stages after `coalescing.stage_retention_seconds`.
Set this retention longer than the longest expected staging operation. Recovery
may invalidate a slow stage, causing its publisher to fail and require a retry.
Versioned Storage's upload deadlines, cleanup grace, filesystem and database
failure limitations also apply. External writers and older application versions
that bypass this protocol are not fenced: drain old workers and deploy the mode
consistently before enabling it. Disabling or changing the database while work
is outstanding also breaks coordination.

Pending rendered HTML is stored as plaintext JSON in the database until work
completes, and may persist in database backups, replicas, logs, or failed-job
records. Restrict database and backup access and apply appropriate retention
policies. Target ordering rows and fingerprints remain after completion to keep
old snapshots fenced; do not delete them while old work or snapshots may exist.
Only trusted processes should be allowed to modify these tables.

Before deleting a document's underlying record, the application can fence
existing and future registrations:

```php
Documents::tombstoneTarget($document->target());
// To deliberately allow new work for this target later:
Documents::restoreTarget($document->target());
```

Tombstoning supersedes existing snapshots, clears pending work, and rejects new
registrations until an explicit restore. Previously captured snapshots remain
superseded after restoration. These operations may run inside the same
Laravel-managed transaction as the record deletion or restoration **when both
use the same database connection**; a rollback restores the previous state.
Neither operation physically deletes published PDFs or prevents writers that
bypass this protocol. `Documents::invalidate($target)` remains available when
only existing snapshots should be superseded without blocking new registrations;
it does not clear an existing tombstone.

### Document events

Generation and publication emit the existing lifecycle events:

- `DocumentGenerator` emits `DocumentRendering` before PDF generation, including
  when using `generate()` without publishing. This event name refers to PDF
  generation, not rendering the Blade view.
- `DocumentPublisher` emits `DocumentStored` after storage succeeds, with the
  version identifier or `null`. It never emits a generation-start event.
- With latest-snapshot-wins enabled, superseded publication emits
  `DocumentSuperseded` without storing or emitting `DocumentStored`.
- Either stage emits `DocumentRenderFailed` if it throws, with the exception
  class and message; the original exception is rethrown.

The events in `SkyRaptor\LaravelDocuments\Events` expose `target` and
`generationId`, not the snapshot HTML. The target contains the storage
identifier and context, not a storage service. Contexts and failure messages
can still contain sensitive information. A failed attempt can leave partial
files and can later be retried.

The generation ID is created with the job and survives queue serialization and
retries. Direct generation creates a new ID unless
`generate($rendered, generationId: $id)` supplies one explicitly. The generated
result owns that ID; publication preserves it. At the document level, use
`Documents::generate($document, generationId: $id)` or
`Documents::publish($document, generationId: $id)`. An existing generated
result's ID cannot be overridden.
A duplicate unique job is discarded and emits no events for its ID. Listener
exceptions are reported to Laravel and do not alter the storage result; Laravel
may stop invoking later listeners. Use asynchronous queued listeners when they
need independent retries. Event delivery is best-effort, not crash-proof.

### Jobs, progress, and batches

`Documents::makeJob()` and `makeJobIfChanged()` choose the explicit `job:` argument,
then the document's configured job, then the storage configuration's default.
They also accept `connection:` and `queue:` arguments.
Built-in jobs preserve their existing connection and queue when the corresponding
argument is omitted or `null`; non-null arguments override only that setting.
The lower-level `DocumentJobFactory::make()` accepts a snapshot instead; pass
`job: $document->job()` to preserve the document's job setting when using it
directly.
Call `withGenerator(CustomGenerator::class)` on the returned job to select a
custom generator. Extend `DocumentGenerator` and override
`protected generateContents(RenderedDocument $rendered): string` to customize
the final PDF bytes while preserving generation IDs and events. Constructor
dependencies are resolved from the worker's container. Jobs generate once per
execution and pass that result to `DocumentPublisher`.
Jobs implement
`Jobs\Contracts\GenerateDocument`. Usually extend `GenerateUniqueDocument` for
unversioned storage or `GenerateVersionedDocument` for versioned storage, so
their uniqueness and batch rules are retained. The base jobs expose `generate()`,
`generated()`, and `version()` to custom handlers and middleware. A job running
on a worker does not update the original dispatching-side object.

#### Optional Mateffy Job Progress integration

Install the optional progress package:

```bash
composer require mateffy/laravel-job-progress:^2.2
```

Select one of the built-in jobs:

```php
use SkyRaptor\LaravelDocuments\Integrations\JobProgress\GenerateUniqueDocumentWithProgress;
use SkyRaptor\LaravelDocuments\Integrations\JobProgress\GenerateVersionedDocumentWithProgress;

// For disk storage:
public static ?string $job = GenerateUniqueDocumentWithProgress::class;

// For versioned storage instead:
public static string $storage = 'versioned';
public static ?string $job = GenerateVersionedDocumentWithProgress::class;
```

Save `$job->generationId()` before dispatch; later query
`GenerateUniqueDocumentWithProgress::getProgress($id)` or
`GenerateVersionedDocumentWithProgress::getProgress($id)` as appropriate.
Query the concrete job class when using a subclass. Progress can be `null` until
the job starts. On completion, its result is the version identifier or `null`
for unversioned storage. The integration does not provide intermediate
PDF-render percentages. Protect progress lookups; failure messages may contain
sensitive details.

The built-in jobs support individual cancellation before rendering; versioned
jobs also check batch cancellation. Cancellation is cooperative and cannot stop a
render already in progress. The integration uses Mateffy's progress error
handling unchanged. Progress failures can fail the job even after the PDF was
stored; queue retries may overwrite it or publish another version. For customization,
see [TrackedVersionedDocument](examples/TrackedVersionedDocument.php). If
subclassing a tracked job, add Mateffy's `#[Cancellable]` attribute again to the
concrete subclass to enable cancellation.

The contract and `generate()` also allow integrations with other progress
packages without depending on Mateffy. A custom job that implements the contract
without extending the base jobs may reuse `TracksDocumentProgress`; it must also
implement `HasJobProgress` and provide `documentBatchCancelled(): bool`.
Custom job and generator classes used on queues must be named and autoloadable by
every worker.

#### Batches

Only batch non-unique jobs with storage that permits multiple writes, such as
`GenerateVersionedDocumentWithProgress` with `versioned` storage. Configure
Laravel's [batch table and workers](https://laravel.com/docs/12.x/queues#job-batching)
and use an asynchronous queue: the database batch repository executes `sync`
jobs inside a transaction, which versioned storage rejects.

Laravel batch progress counts successful jobs, including cancelled jobs that
return normally; failed jobs are tracked separately and individual percentages
are not aggregated. Store both the batch ID and each generation ID when both
kinds of progress are needed.

`GenerateUniqueDocument` and its tracked subclass reject batching because
Laravel does not acquire unique locks for batched jobs. Dispatch them
individually; unique locks are shared across subclasses for the same target.
Custom unique jobs using Laravel's `SerializesModels` also release that shared
lock when Laravel deletes or fails the job because a related model is missing.
The model must not be part of the frozen document input.

### Upgrading from the previous API

Unique jobs now expose a hash of the storage-context identity through `uniqueId()`,
while retaining the same underlying target lock
keys. Drain old unique-job payloads before deploying this change: their saved
missing-model cleanup metadata cannot be repaired retroactively. Locks already
leaked by missing-model cleanup need to be removed manually.

The skeleton-only `LaravelDocuments` service and facade, placeholder command,
translation, and migration were removed. Previously published copies and any
placeholder table remain in applications until explicitly removed.

This architecture changes the snapshot, target, storage, and job contracts.
Drain or replace queued jobs created with the old serialized payload before
deploying. Replace storage class properties with registered identifiers and
move storage options to manager registrations. Existing disk `.hash` sidecars
and versioned `document.hash` files are left untouched; old version directories
remain readable, but change detection now starts from the shared snapshot cache.

`Document::renderer()` and `DocumentRendererHandler` were removed. Use the
`Facades\Documents` facade or inject `DocumentWorkflow` for document-level
generation, publication, and job creation. For explicit revision control, capture
`RenderedDocument` once with `Document::render()` (formerly `snapshot()`).
`DocumentSnapshot` is now `RenderedDocument`, and `DocumentRenderer` is now
`DocumentGenerator`. Generation returns `GeneratedDocument` instead of a string;
read PDF bytes from `contents` and pass that result to `DocumentPublisher::publish()`
or `Documents::publish()`. Publication no longer accepts rendered input at the
low level or regenerates PDF bytes. `DocumentJobFactory` and
`DocumentSnapshotCache::changed()` still consume rendered input.
Replace job `withRenderer()` calls with `withGenerator()` and move custom
byte generation to `generateContents()`. Generation IDs are generation arguments
and are carried by the generated result, not mutable generator state.
The `snapshot_cache` configuration and existing event class names are unchanged.

The default PDF driver now uses Spatie's configured driver and does not apply
the former hard-coded Browsershot flags, network-idle wait, or Sail/production
sandbox overrides. The builder-level PDF cache is disabled by default. Driver
registration callbacks now receive `PdfBuilder` rather than `PdfOptions`;
replace property assignments with builder methods such as `format('A4')`.
Register an explicit driver configuration when those behaviors are required, and review the
security implications before disabling browser security features.
